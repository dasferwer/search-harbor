# Оценка качества поиска

Скрипт сравнивает четыре фиксированных режима: `lexical`, `semantic`, `hybrid` и `rerank`. Запросы и оценки релевантности заранее записаны в `data/queries.json`. В наборе 12 запросов для выбора режима (`dev`) и 24 для отдельного отчёта (`test`). Тексты между частями не повторяются; в обеих есть точные названия, опечатки и описания потребности своими словами.

Это авторский синтетический набор. Запросы, каталог и оценки подготовлены для этого проекта, независимой разметки людьми здесь нет. Разделение dev/test помогает не выбирать режим по тестовым цифрам, но не превращает небольшой набор в независимый промышленный бенчмарк. При доработке поиска нельзя менять тестовые запросы и оценки ради улучшения результата; для следующего эксперимента нужен новый версионированный набор.

## Как повторить

После `make up` и завершения первой индексации:

```bash
uv run python scripts/evaluate.py --url http://localhost:8220 --output docs/evaluation.json
```

Скрипт до пяти минут ждёт `/ready`. Отдельный запрос ограничен 30 секундами, весь прогон — 30 минутами. Эти значения можно изменить через `--ready-timeout`, `--request-timeout` и `--max-duration`. По умолчанию каждый запрос повторяется три раза (`--repeats`), запросы идут последовательно. До замеров выполняются два прогревочных запроса на режим; их время не входит в результат. Порядок режимов меняется по кругу, чтобы один режим не всегда измерялся первым.

Во время прогона не меняйте каталог и не переключайте индекс. Скрипт проверяет имя поколения, последовательности каталога и индекса и отсутствие отставания. Изменение этих значений или разные семейства в повторных ответах прерывают прогон, чтобы несопоставимые результаты не попали в готовый отчёт. Завершённый JSON записывается атомарно; при ошибке предыдущий файл остаётся историческим результатом со своим временем.

## Что измеряется

В каждом запросе передаётся `limit=5` и `distinct_families=true`. Оценка идёт по семействам товаров: сто почти одинаковых вариантов одного товара не должны занимать всю выдачу и улучшать метрику.

| Метрика | Расчёт |
| --- | --- |
| Recall@5 | Число найденных релевантных семейств среди первых пяти, делённое на число всех размеченных релевантных семейств запроса. |
| NDCG@5 | DCG с выигрышем `2^grade - 1` и скидкой `log2(rank + 1)`, делённый на DCG идеального порядка. |
| MRR | Среднее значение величины, обратной позиции первого релевантного семейства; если его нет в первых пяти, вклад равен нулю. Это усечённый MRR@5. |
| p50 / p95 | Процентили времени последовательных HTTP-запросов после прогрева, с линейной интерполяцией между наблюдениями. |

Оценки семейства: 3 — прямо соответствует потребности, 2 — полезная альтернатива, 1 — связано с задачей, но решает её лишь частично. Все положительные оценки считаются релевантными для Recall и MRR; NDCG учитывает разницу между ними. Неразмеченные семейства имеют оценку 0. Качество усредняется по запросам с одинаковым весом, задержки — по всем измеренным HTTP-повторам.

Сначала выполняется dev. Рекомендуемый режим выбирается по NDCG@5, при равенстве — по MRR, затем Recall@5. Полная ничья разрешается фиксированным порядком `lexical → semantic → hybrid → rerank`. После фиксации выбора запускается test и публикуются метрики всех четырёх режимов. Рекомендация по тестовому результату не меняется.

`docs/evaluation.json` содержит итоговые метрики обеих частей, выбор по dev, ответы и задержки каждого запроса, градации релевантности и SHA-256 файлов каталога, запросов, seed и скрипта оценки. Хеш каталога относится к исходным описаниям семейств; это не хеш выгрузки рабочей базы. Имя индекса и последовательности в `stable_snapshot` позволяют связать результат с состоянием работающего сервиса.

## Границы результата

- В каталоге 30 вручную описанных семейств. Seed по умолчанию создаёт 100 близких вариантов каждого: меняются SKU, цена и наличие, но не смысл описания. 3 000 строк не означают 3 000 независимых поисковых потребностей.
- Семантический поиск использует готовую англоязычную BGE-модель, переранжирование — готовую MiniLM. В проекте они не дообучаются. Этот набор не оценивает русский язык, многозначные запросы и категории товаров, неизвестные модели.
- 24 тестовых запроса слишком мало для надёжного вывода о превосходстве одного подхода. Нет независимой разметки, доверительных интервалов и проверки на реальном пользовательском трафике.
- p50/p95 описывают локальный прогретый последовательный запуск. Повторные запросы могут использовать кеши. Это не нагрузочный тест, не измерение холодного старта, не производительность кластера и не SLA.
- Оценивается релевантность семейств среди доступных товаров. Точность фильтров, изменение цен, удаление, идемпотентность и восстановление индекса проверяются отдельными интеграционными и аварийными сценариями.

## Завершённый локальный прогон

13 сентября 2026 года, 3 000 живых SKU, active cursor и catalog sequence — 3 008. Полный отчёт с каждым запросом: [evaluation.json](evaluation.json).

| Режим | Test Recall@5 | Test NDCG@5 | Test MRR@5 | p50, мс | p95, мс |
| --- | ---: | ---: | ---: | ---: | ---: |
| lexical | 0,9792 | 0,9395 | 0,9236 | 8,35 | 10,42 |
| semantic | 1,0000 | 1,0000 | 1,0000 | 6,95 | 12,51 |
| hybrid | 0,9792 | 0,9812 | 0,9792 | 10,89 | 14,71 |
| rerank | 1,0000 | 0,9792 | 0,9722 | 99,80 | 136,24 |

По результатам dev до запуска test выбран `semantic`. На этом наборе cross-encoder не улучшил результат семантического поиска и увеличил задержку. В API демонстрационным режимом по умолчанию остаётся `hybrid`; для выбранного по dev режима передавайте `mode=semantic`.

Идеальные числа semantic означают, что текущий небольшой синтетический набор оказался лёгким для этой модели. Их нельзя переносить на реальный магазин. Следующий содержательный эксперимент потребует разнообразного каталога, независимой разметки и новых, заранее зафиксированных запросов. Приведённые задержки измерены последовательно на прогретом локальном стенде; кеш повторных запросов входит в эти условия.
