# Эксплуатация локального стенда

Все команды выполняются из папки проекта. Они относятся к Compose-проекту `22-search-harbor`. В примерах используется токен из `.env.example`; если он изменён, передавайте своё значение.

## Первичная проверка

```bash
docker compose ps -a
curl -sS http://localhost:8220/health
curl -sS http://localhost:8220/ready
curl -sS http://localhost:8220/admin/status \
  -H 'X-Admin-Token: local-demo-searchharbor-admin-change-before-deployment'
docker compose logs --tail=100 api worker opensearch models migrate
```

Успешные `models` и `migrate` должны завершиться с кодом 0. API может быть healthy, пока первое поколение ещё building. Готовность поиска определяется `/ready`, а прогресс — сравнением `generations[].cursor` и `catalog.sequence` в административном ответе.

Для индексатора heartbeat означает, что процесс достигает PostgreSQL. Если heartbeat живой, но cursor стоит и `error` заполнен, изучайте ошибку и OpenSearch; перезапуск без устранения причины её не исправит.

## Не скачались модели

Посмотрите `docker compose logs --tail=100 models`: этот одноразовый контейнер получает конкретные revisions из Hugging Face. Проверьте доступ машины в интернет и место для volumes. После устранения причины повторите `make up`.

Не подставляйте случайные веса под старое имя и не меняйте `model_hash` вручную. При несовпадении embedding-модели с уже записанной в PostgreSQL API и worker отказывают в работе. Чтобы вернуть существующий каталог, восстановите прежние файлы из закреплённого revision и пересоздайте процессы:

```bash
docker compose run --rm models
docker compose up -d --force-recreate api worker
```

Переход на другую модель требует отдельной миграции; POST rebuild сам по себе её не выполняет.

## OpenSearch остановлен

При недоступном OpenSearch поиск отвечает ошибкой доступности. Изменения каталога могут продолжать сохраняться в PostgreSQL. После восстановления брокер не нужен: worker читает сохранённые события со своего курсора.

```bash
docker compose start opensearch
docker compose logs --tail=100 opensearch worker
```

Дождитесь готовности OpenSearch, затем проверьте `/ready` и движение курсоров. Если контейнер завершился из-за нехватки памяти, устраните причину в настройках Docker перед повторным запуском; индексатор не может исправить постоянно падающий поисковый движок.

## Worker упал после bulk

```bash
docker compose up -d worker
docker compose logs --tail=100 worker
```

Курсор не переносится вручную. Если bulk успел примениться, а commit нет, повторная пачка с теми же версиями допустима. При ошибке отдельного bulk-элемента в лог попадёт тип первой ошибки; курсор останется перед пачкой. Сначала устраните причину, затем дайте worker повторить её. Пропуск события вручную нарушит воспроизводимость следующей сборки.

Если был включён `WORKER_AFTER_BULK_DELAY` для аварийного сценария, верните обычный режим:

```bash
WORKER_AFTER_BULK_DELAY=0 docker compose up -d --no-deps --force-recreate worker
```

## Потерян активный индекс

Признаки: в статусе поколения `Index missing; request rebuild`, `/ready` и поиск недоступны. Worker не создаёт пустой индекс со старым курсором. Запустите восстановление истории в новое поколение:

```bash
curl -sS -X POST http://localhost:8220/admin/rebuilds \
  -H 'X-Admin-Token: local-demo-searchharbor-admin-change-before-deployment'
```

Следите за building через `/admin/status`. После догонки worker переключит active, и `/ready` снова станет успешным. При потерянном active сохранение каталога остаётся доступным, но бесшовного поиска во время восстановления нет: прежнего индекса уже не существует.

Если потерян индекс поколения building, worker сначала отдельной транзакцией сохраняет cursor=0. На следующем шаге он создаёт индекс заново и повторяет историю. Прежний active продолжает работать, если его индекс цел. Не переносите cursor вперёд и не помечайте building активным вручную.

## Достигнут предел поколений

После десяти записей `/admin/rebuilds` отвечает 409. Автоматической очистки нет. Сначала сохраните список поколений из `/admin/status` и решите, какие `retired` больше не нужны. Не удаляйте active или building.

Ручная очистка должна учитывать два объекта: соответствующий индекс OpenSearch и строку `generations` в PostgreSQL. Удаление только индекса не освобождает лимит строк. Перед обслуживанием остановите API и worker, чтобы запросы, уже выбравшие старое имя, не потеряли индекс во время выполнения:

```bash
docker compose stop api worker
```

Точного автоматического сценария архивирования в проекте нет: старые индексы и метаданные удаляются оператором только после выбора конкретных retired-имён. Затем верните сервисы командой `docker compose up -d api worker` и проверьте `/ready`. Журнал `events` нужен для последующих пересборок, его очистка не является частью этой операции.

## Товар не находится после изменения

Сначала проверьте `GET /products/{sku}`: это актуальная запись PostgreSQL. Затем сравните курсор active с `catalog.sequence`. Даже после догонки действует refresh OpenSearch. Старое попадание с другой версией API скрывает, а не заменяет ему цену на лету.

Проверьте фильтры: по умолчанию `in_stock=true`, категория и бренд сравниваются точно. `distinct_families=true` отдаёт только один вариант семейства. Во время обновления после удаления устаревших кандидатов API не добирает выдачу до `limit`.

## Проверки и данные

`make test` использует `test-db` и `test-search` с tmpfs, а не рабочие volumes. После тестов временные сервисы можно остановить:

```bash
docker compose --profile test stop test-db test-search
```

Smoke создаёт демонстрационные изменения в работающем каталоге. Recovery запускайте на локальном стенде: он управляет его контейнерами и проверяет повторное выполнение после сбоев. Конкретные результаты завершённых прогонов сохраняются отдельно от этого руководства.

`make evaluate` запускайте без параллельных изменений каталога и пересборок. Он сравнивает четыре режима; протокол и ограничения описаны в [evaluation.md](evaluation.md). Повторный seed не откатывает ручные изменения, поэтому он не возвращает каталог к исходному состоянию для сравнения.

`docker compose stop` сохраняет контейнеры и данные, `make down` удаляет контейнеры и сеть, сохраняя volumes. `docker compose down -v` удалит рабочий каталог, историю, индексы и скачанные модели; это не способ обычного восстановления.
