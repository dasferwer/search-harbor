# SearchHarbor

[![Проверки](https://github.com/dasferwer/search-harbor/actions/workflows/ci.yml/badge.svg)](https://github.com/dasferwer/search-harbor/actions/workflows/ci.yml)

Поиск по англоязычному каталогу с BM25, смысловым поиском и переранжированием. PostgreSQL хранит товары и историю изменений, OpenSearch — поисковые индексы. Новый индекс собирается рядом с действующим и становится активным после обработки всех изменений.

Главная задача проекта — совместить поиск с обычной жизнью каталога: изменениями цен, удалением товаров, повторами запросов, недоступностью поискового движка и пересборкой индекса. Результаты поиска сверяются с актуальными версиями товаров в PostgreSQL, чтобы отставший индекс не показывал прежнюю цену или удалённый товар.

Стек: Python 3.12, FastAPI, PostgreSQL 17, SQLAlchemy, Alembic, OpenSearch 3.2, FastEmbed/ONNX Runtime, Docker Compose. Проект для портфолио с запуском на локальном стенде.

## Запуск

Нужен запущенный Docker с Compose. Для проверок на хосте — Python 3.12 и `uv`.

```bash
cp .env.example .env
make up
```

При первом запуске сервис `models` скачает веса двух моделей в отдельный volume. Для этого нужен интернет. `migrate` применит миграцию и заполнит каталог. Эти два контейнера завершаются после выполнения своей работы; API, worker, PostgreSQL и OpenSearch продолжают работать.

Документация API: [localhost:8220/docs](http://localhost:8220/docs). `GET /health` проверяет API и доступ к БД, `GET /ready` — наличие активного индекса, доступ к нему и совместимость embedding-модели. До окончания первой индексации `/ready` возвращает 503. Зелёный healthcheck API сам по себе не означает, что поиск уже готов.

По умолчанию seed создаёт **3 000 SKU из 30 синтетических семейств**: по 100 вариантов с разными ценами и наличием, но одинаковым смысловым описанием. Это не 3 000 независимо размеченных товаров. Число вариантов задаёт `CATALOG_VARIANTS` в `.env`; повторный seed добавляет отсутствующие SKU и сохраняет уже изменённые товары.

## Четыре режима поиска

| `mode` | Что выполняется |
| --- | --- |
| `lexical` | BM25 по названию и описанию, английский анализатор и нечёткое совпадение для опечаток. Название имеет больший вес. |
| `semantic` | Вектор запроса и приближённый поиск ближайших документов через HNSW. |
| `hybrid` | Оба поиска и объединение позиций через Reciprocal Rank Fusion, `1 / (60 + rank)`. Режим по умолчанию. |
| `rerank` | Гибридный отбор, затем оценка пары «запрос — описание» моделью cross-encoder для первых 60 кандидатов. |

```bash
curl -sS http://localhost:8220/search \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "headphones for a noisy office",
    "mode": "hybrid",
    "category": "audio",
    "max_price": 20000,
    "in_stock": true,
    "distinct_families": true,
    "limit": 5
  }'
```

Цена хранится целым числом в минимальных денежных единицах, без конвертации валют. Доступны точные фильтры `category`, `brand`, диапазон `min_price`/`max_price` и наличие. `in_stock=false` снимает ограничение по наличию; это не фильтр «только отсутствующие». `distinct_families=true` оставляет по одному представителю семейства. Максимальный `limit` — 50.

Ответ содержит товары, позиции в исходных списках, итоговый `score`, имя поколения, `indexed_sequence`, `catalog_sequence` и `lag_events`. Во всех режимах, кроме `rerank`, итоговый score вычисляется по позициям; исходные оценки BM25 и cosine similarity не возвращаются. После переранжирования исходное значение остаётся в `rrf_score`. Эти числа нельзя трактовать как вероятность покупки или сравнивать напрямую между режимами.

## Модели

Здесь работают настоящие готовые модели на CPU, без внешнего inference API и без обучения в проекте:

| Назначение | Модель и зафиксированный источник |
| --- | --- |
| Embeddings, 384 измерения | `BAAI/bge-small-en-v1.5`; ONNX-файлы `qdrant/bge-small-en-v1.5-onnx-q`, revision `52398278842ec682c6f32300af41344b1c0b0bb2`. |
| Переранжирование | `Xenova/ms-marco-MiniLM-L-6-v2`, revision `a09144355adeed5f58c8ed011d209bf8ee5a1fec`. |

Точный список файлов и загрузка закреплены в [models.py](src/searchharbor/models.py). Для embedding-файлов считается fingerprint; он входит в ключ кеша документов и сверяется между API, worker и состоянием каталога. Подмена модели не запускает незаметное смешивание несовместимых векторов. Hot swap модели в этой версии не реализован. Повторные тексты документов используют кеш в PostgreSQL, запросы — ограниченный кеш в памяти процесса. Реранкер загружается при первом обращении к режиму `rerank`.

## Изменение каталога

Поиск и чтение товара публичны внутри локального стенда. Изменения требуют `X-Admin-Token`. Демо-токен из `.env.example`:

```text
local-demo-searchharbor-admin-change-before-deployment
```

Создание нового SKU:

```bash
curl -sS -X PUT http://localhost:8220/admin/products/demo-headphones \
  -H 'X-Admin-Token: local-demo-searchharbor-admin-change-before-deployment' \
  -H 'If-Match: 0' \
  -H 'Idempotency-Key: create-demo-headphones-1' \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Office noise cancelling headphones",
    "description": "Over ear headphones for focusing in a busy office, with soft ear cushions.",
    "category": "audio",
    "brand": "demo",
    "family": "demo-headphones",
    "price_cents": 9900,
    "in_stock": true
  }'
```

Ответ содержит `version`. Для изменения сначала прочитайте `GET /products/demo-headphones`, затем передайте эту версию целым числом в `If-Match`, новое полное тело товара и новый `Idempotency-Key`. Здесь `If-Match` — числовая версия из JSON, без HTTP ETag и кавычек. Несовпадение версии даёт 409. Удаление выполняется через `DELETE /admin/products/{sku}` с теми же заголовками и текущей версией, без тела.

Одинаковый ключ и одинаковый запрос возвращают сохранённый результат. Повторное использование ключа с другим телом, SKU, версией или действием даёт 409. Для нового изменения нужен новый ключ. Удаление оставляет запись с новой версией и признаком `deleted`; позднее старое событие не должно вернуть товар в поиск.

Товар, событие и результат идемпотентного запроса фиксируются одной транзакцией. Worker читает журнал `events` из PostgreSQL. Отдельного RabbitMQ здесь нет: источником повторной доставки служат журнал и курсор каждого поколения.

## Пересборка индекса

```bash
curl -sS -X POST http://localhost:8220/admin/rebuilds \
  -H 'X-Admin-Token: local-demo-searchharbor-admin-change-before-deployment'

curl -sS http://localhost:8220/admin/status \
  -H 'X-Admin-Token: local-demo-searchharbor-admin-change-before-deployment'
```

Новое поколение индекса читает историю с начала. Действующий индекс продолжает обслуживать поиск, пока новый не догонит каталог. Переключение указателя происходит в PostgreSQL; уже начавшиеся запросы могут завершиться на прежнем индексе. Старые поколения сохраняются со статусом `retired`.

Одновременно разрешена одна сборка. Всего сохраняется до десяти записей поколений, затем API вернёт 409. Автоматической очистки и API удаления поколений нет. Потеря активного OpenSearch-индекса требует явного запроса rebuild: worker не создаёт пустой индекс со старым курсором и не выдаёт его за восстановленный.

Обновления появляются в поиске с задержкой. Помимо очереди событий есть refresh OpenSearch. Даже при нулевом `lag_events` последнее изменение может ещё не быть видно поиску. Сверка версий с PostgreSQL убирает устаревшие попадания, поэтому некоторое время выдача может быть короче `limit`. Новые товары появятся после индексации и refresh.

## Проверки и оценка

```bash
make check
make test
make smoke
make recovery
make evaluate
```

`make check` устанавливает зафиксированные зависимости разработки и запускает Ruff. `make test` использует отдельные PostgreSQL и OpenSearch в tmpfs. Smoke обращается к работающему API. Recovery управляет контейнерами этого Compose-проекта, чтобы проверить восстановление после сбоев; запускайте его на локальном стенде. Для smoke, recovery и оценки нужен запущенный проект. Если `make check` ещё не запускался, перед командами на хосте выполните `uv sync --extra dev --frozen`.

Методика сравнения режимов и границы выводов: [docs/evaluation.md](docs/evaluation.md). Числа нужно брать из `docs/evaluation.json` конкретного завершённого прогона. Сам размер seed и наличие нейросети не доказывают качество поиска. При оценке каталог должен оставаться неизменным; пользовательские правки после запуска seed сохраняются.

В локальном прогоне прошли 70 тестов, smoke и три сценария восстановления. Все результаты и условия проверки: [docs/verification.md](docs/verification.md).

Подробности: [архитектура](docs/architecture.md), [эксплуатация и восстановление](docs/runbook.md), [объяснение для собеседования](docs/interview.md).

## Границы проекта

Короткий сценарий для интервью:
[SIGKILL после bulk и восстановление отстающего курсора](docs/recovery-flagship.md).

API опубликован только на `127.0.0.1:8220`. У PostgreSQL и OpenSearch нет host-портов, security plugin OpenSearch отключён для внутренней сети демо. Токен в примерах предназначен для локального запуска.

Это один PostgreSQL, один OpenSearch с одним шардом без реплик и один последовательный индексатор. Высокой доступности, распределённого обучения, реальных данных магазина, пользовательской истории и персонализации здесь нет. Каталог и разметка синтетические, модели готовые и англоязычные. PostgreSQL сериализует изменения каталога через общую строку состояния; проект не обещает промышленную пропускную способность.

`make down` останавливает и удаляет контейнеры, сохраняя volumes с каталогом, индексами и моделями. Для обычной паузы подойдёт `docker compose stop`.
